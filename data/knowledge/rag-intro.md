# RAG（Retrieval-Augmented Generation）知识库问答

## 什么是 RAG？

RAG 全称 Retrieval-Augmented Generation，即“检索增强生成”。
它的核心思想非常朴素：**在让大模型回答问题之前，先从知识库中检索出与问题最相关的资料，再把资料拼进 Prompt 里让模型“开卷作答”。**

传统大模型只能依靠训练时学到的知识，存在三个明显痛点：

1. **知识过期**：训练数据有截止日期，无法回答最新信息。
2. **不会“查资料”**：对私有文档、内部资料一无所知。
3. **容易一本正经地胡说八道**：没有依据时，模型倾向于编造答案。

RAG 通过外挂知识库解决了这些问题：把文档提前切块并向量化，用户提问时实时检索最相关的片段，让模型基于这些片段生成带依据的回答。

## RAG 的核心流程

一个典型的 RAG 系统包含两条链路：

### 1. 离线索引链路（文档入库）

```
文档 → 文本解析 → 分块（Chunk） → Embedding 向量化 → 向量库
```

- 文本解析：支持 PDF、Word、Markdown、TXT 等格式。
- 分块：把长文档切成适合向量化的短片段，通常 300~800 字，并保留少量重叠避免语义断裂。
- 向量化：用 Embedding 模型把文本变成高维向量，使语义相近的文本在向量空间中靠得更近。
- 向量库：存储向量和原文的映射，支持快速相似度检索。

### 2. 在线问答链路（用户提问）

```
用户问题 → Embedding 向量化 → 向量相似度 top-k 检索
        → 拼接上下文 + 问题 → LLM 生成带引用的回答
```

- 问题向量化和文档向量化使用同一个 Embedding 模型，保证向量空间一致。
- 检索通常用余弦相似度，找出最相关的 k 个片段。
- 最终答案由大模型生成，但受到检索片段的“约束”，可以追溯到来源。

## 本项目的设计

本项目是一个开箱即用的 RAG 知识库问答服务：

- **LLM**：OpenAI 兼容 Chat API（本项目默认配置 DeepSeek 网关）。
- **Embedding**：本地 BAAI/bge-small-zh-v1.5，中文效果好、体积小，不依赖外部 Embedding API。
- **向量存储**：NumPy 实现的轻量本地向量库，零额外服务，适合快速演示和个人知识库。
- **存储**：SQLite 默认，可一行配置切换 MySQL。
- **前端**：原生 HTML/CSS/JS 聊天界面，支持文档上传。

## 为什么向量检索能“理解”语义？

传统关键词搜索只能匹配字面相同的内容；而向量搜索把文本映射到语义空间后，即使提问用词和原文不同，只要语义相近，检索结果也能命中。

例如：

- 原文：“模型在生成回答时容易产生幻觉”
- 提问：“RAG 为什么能减少胡说八道？”

两者字面差异很大，但语义高度相关，向量检索可以正确召回。
